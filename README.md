# A股主力策略情景推演与分层选股系统

独立于 JCKX Tail Overnight 的新系统：每日 23:00 生成“下一交易日”的全景概率
推演（市场状态 → 次日情景 → 板块职责 → 个股推荐），并通过企业微信推送给用户。

## 核心规则

- 23:00 只在“明天是交易日”时运行并推送；周五、假期中不推，收假前夜推一次且
  纳入整个假期的资讯。
- 当前链路：启动时冻结同花顺实时热榜 Top100 → 严格信息截止过滤 → 跨源去重 →
  DeepSeek 有界影响评估（词典降级）→ 市场状态/次日情景/板块/个股证据融合 →
  最多 5 只达到评分、概率和因子覆盖门槛的新推荐。
- 个股采用 100→30→12→5 分层漏斗：100 支先做硬过滤和基础评分，前 30 支做
  个股主力阶段、个股情绪和一日游风险规则分析，前 12 支再由 DeepSeek 结合行情、
  资金、行业、新闻和公告做深度分析，最后最多输出 5 支。
- 正式推荐先进入 `pending_entry`，目标交易日开盘 15 分钟确认条件真实触发后才转为
  `active` 并持续预测；未触发则保持现金并关闭该次跟踪。
- “主力/操盘行为”只作为竞争性假设输出，同时列出支持证据、反证和次日验证条件，
  不把不可观测主体写成确定事实。
- 散户情绪、追涨拥挤和量化收割目前使用市场宽度、涨跌停结构、板块分化、量能、
  上影线和指数/个股宽度背离形成可审计代理分，不宣称能够直接观测真实账户身份。
- 原系统（jckx-tail-overnight）不动：不 import 其代码、不写其数据目录、不用其
  锁名与 cron。仅允许只读复用其事件缓存与分钟档案，且必须带版本校验和直连兜底。
- 共享：同一台服务器、同一 Tushare token、同一企业微信 webhook、同一 JCKX 报告
  密码；报告只走 WireGuard 内网。
- 新闻/政策/公告多免费源接入：财联社电报、巨潮公告、中国政府网与部委政策库；
  跨源标题去重、每源覆盖监控，资讯或 LLM 影响评估不足时进入 `facts_only` 并取消
  新推荐；已有跟踪股票继续生成降级方向判断。重大政策和公告额外归档正文快照、
  做事实抽取与原文片段核验。
- 常规候选与防守候选共用 ST/板块/市值/流动性/上市天数/过热硬过滤；估值异常采用扣分而非一刀切。前一日涨停股不再直接剔除，而是进入连续强势专用执行计划；目标日封死涨停仍不模拟成交。
  目标板块在形态筛选前不会被全市场榜单截断。
- “避风港”会先把同行业龙虎榜买卖资金净额相抵，再校验净流入金额、正流入个股数/
  占比、个股 MA20 结构、收盘位置和直接资金方向，不能仅凭行业总买入额入选。
- 主推荐、反包、修复、避风港各自冻结机器可读的 15 分钟执行计划；必须取得完整
  15 根确认线，成交价取确认时点价格。观察/回避层不回放、不计收益，历史开盘价代理
  样本与新口径隔离。
- 报告明确区分数据截止日、预测目标日和运行模式；目标日前涨跌不作为预测结果，
  推送失败也不会标记为正式预测。
- 模型只有同时通过冻结验证、滚动样本外或逐日稳定性、含成本组合对照时才可晋级；
  任一门槛缺失即继续使用已批准产物或规则链路。

## 运行方式

```bash
python3 -m venv venv
venv/bin/pip install -r requirements.txt
cp .env.example .env   # 填入 Tushare token、企业微信 webhook、AI key

./run.sh check-calendar          # 明天是否交易日、今晚是否推送
./run.sh data-backfill --years 3 # 首次历史数据回灌（耗时较长）
./run.sh data-update             # 增量更新当日数据
./run.sh nightly --no-push       # 生成今晚报告但不推送（自检）
./run.sh nightly                 # 正式夜间运行并推送
./run.sh tail-review --no-push   # 14:50 尾盘热门股与模拟持仓复评（不推送）
./run.sh train                   # 模型训练（低峰时段，全自动）
./run.sh health                  # 健康检查
```

## 调度（独立 cron）

- 每天 23:00：`nightly`（明天不是交易日则静默退出）
- 交易日 14:50、14:52、14:54、14:56：`tail-review`（首次成功后跳过；推送失败自动重试）
- 每天 23:08：`health`（核验夜间运行、资讯证据状态与推送）
- 每周六 02:00：`train`（模型重训，不阻塞 23:00 推理）
- 报告服务：`@reboot` + 每 5 分钟 watchdog，监听 `127.0.0.1:8082`，nginx
  `/strategy/` 反代，仅 WireGuard 内网可访问。

```text
src/market_strategy/

├── storage.py         # SQLite：交易日历/日线/每日指标/事实/预测日志

├── features/          # 市场宽度/板块/个股特征
├── models/            # 状态识别/转移/情景/板块/个股 + 校准
├── nlp/               # 政策/公告原文事实抽取
├── pipeline.py        # 23:00 编排
├── report.py          # HTML 日报
└── push/wecom.py      # 企业微信摘要推送
```

本系统只生成研究与概率推演，不自动下单，不构成投资建议。
# 盘中入场提醒

正式夜间推荐先进入 `pending_entry`。交易日 09:35 后，`monitor-entry` 会按冻结执行计划持续检查到默认 10:15：高评分、高概率、低一日游风险且催化持续性较强的普通候选，可在第 5 分钟先走“早盘强势确认”；未通过早确认时继续等待第 15 分钟标准 VWAP 确认。其余普通候选仍最早 15 分钟确认；前一日涨停但仍有正常成交机会的候选最早 5 分钟确认。早盘拉升过快、冲高回落或位于涨停价均不会按普通成交假设追入。满足条件后立即激活跟踪、按实际确认价重算止损，并通过企业微信只推送一次。推送失败会在下一轮自动重试。

```bash
./run.sh monitor-entry
```

`setup_cron.sh` 默认在交易时段每分钟执行一次。Tushare 6000 积分不自动包含实时分钟行情；系统默认使用已有分钟源回退链，另购 Tushare 实时行情权限后可设置 `ENABLE_TUSHARE_REALTIME_MINUTE=1`。

`tail-review` 不读取真实账户，只管理系统模拟持仓。它不是把收盘后夜间模型直接套在未收盘数据上，而是运行同口径的尾盘适配链：读取前夜正式候选与当日热榜前列，获取最新分钟线并合成截至决策时点的当日日线，重新执行统一 ST/板块/市值/流动性/上市天数/过热过滤和个股复合评分，再融合夜间评分、热榜位置与尾盘结构进行完整重排。热榜新发现不会伪造夜间模型概率；最终结果执行行业和概念集中度限制。对模拟持仓输出继续持有、转弱观察、止损/利润保护退出或 T+1 锁定次日退出；尾盘新入场会直接记为系统模拟成交。热榜默认不得早于决策时点 15 分钟，分钟线默认不得早于 10 分钟；陈旧热榜会使本轮失败并重试，陈旧持仓行情会明确标记为“无法可靠判断”且保持原状态。

这里的“完整重排”是指完整执行**尾盘时点可观测**的个股选股链，不是假装已经取得收盘后才会完整落地的最终日线、`daily_basic`、收盘资金和公告汇总。`setup_cron.sh` 安装新任务时还会主动删除旧 `/home/ubuntu/jckx-tail-overnight` 的 `run.sh` 定时任务，避免旧尾盘推送被重复启用；旧目录若仅用于共享分钟数据或历史报告服务，可以保留。

集合竞价权限通过 `ENABLE_TUSHARE_OPEN_AUCTION=1` 开启，并严格按信息时点拆分：`stk_auction_o` 提供历史开盘竞价，`stk_auction_c` 提供历史收盘竞价，两者用于夜间评分和回测；`stk_auction` 在目标交易日盘中读取，用于入场确认留痕，不会提前写入前一晚预测。
